SQL Server Performance Audit

Sample engagement on public data · StackOverflow2010 database · SQL Server 2025 (17.0.1000.7) Express Edition (64-bit) · baseline captured 2026-10-30 16:51

Summary

Six changes cut the CPU of the app's calls by 89% and their logical reads by 95%. In the same 20 minutes, the same four workers finished 12 times as many calls. No query returns a different answer: 34 test calls were compared row by row before and after.

Two procedures used 93% of all CPU. The tag page read the whole 6.6 GB posts table on every call. The vote counter scanned all 10 million votes to count the votes of one post. Both now read a small index. Page views no longer wait behind the tag page: their writes waited 633 ms on average before, and 0 ms after.

All six changes are indexes or small procedure edits. None needs an application release. Each one has a rollback script. Most of them touch objects the app vendor owns, so section 5 lists what to clear with them first.

2. The fixes

Each fix was measured the same way: one warm-up call, then the median of five calls, from SET STATISTICS IO, TIME. CPU time comes in steps of about 16 ms, so 0 ms means less than one step. Every row each call returned was saved before and after the change and compared in SQL with EXCEPT both ways. The fixes are numbered in the order they were applied.

Fix 01. Index the votes by post

Every question page shows a vote breakdown. To count the votes of one post, SQL Server read all 10 million votes. The fix is one index on Votes (PostId, VoteTypeId).

Result

Cost
14 s to build. A vote insert reads 10 pages before and 13 after.

Fix 02. Stop the implicit conversion in the CRM lookup

The external contact id column is varchar(20). The procedure takes nvarchar(20), which is what .NET sends by default. So SQL Server converted every row of the index to nvarchar and scanned it, to find one row. The new version converts the parameter once and seeks. It then re-checks the found row with the original comparison, so no input can match a different row than before. The procedure signature does not change.

Result
974 reads → 9. 16 ms CPU → 0 ms. This is the most frequent read after page views.
Proof
Same result: 6 of 6 calls identical, 5 rows compared with EXCEPT both ways, row order included. 1 call returns no rows on both sides; it shows cost only, not identity.
Also tested

Fix 03. Make the month report seek

The report filtered with YEAR(CreationDate) = @Year AND MONTH(CreationDate) = @Month. A function around a column hides it from the index, so SQL Server computed both functions for all 3.7 million posts. A range from the first day of the month to the first day of the next selects the same rows and seeks. An invalid month still returns no rows instead of an error.

Fix 04. Give search and the tag page a narrow index

Both procedures filter with LIKE '%term%'. A leading wildcard can never seek, so both read every question, from the clustered index that also holds every post body. The fix keeps the queries as they are and gives them less to read: a new index on Posts (PostTypeId, CreationDate) with only the columns they use. Search can now stop after its first 50 hits, because the index is already in date order. The tag page also looked up every answer of every matching question; adding Score and OwnerUserId to the vendor's IX_Posts_ParentId removed those lookups.

Result
Search 'memory leak': 610,002 reads → 640. A search with no match: 61.9 s → 1.8 s. Tag 'c#': 6.2 s → 1.5 s.
Cost
22 s to build both. The new index is 161 MB after fix 05. Votes now also update IX_Posts_ParentId, because it carries the score.
Left over
The tag page still runs LIKE over every question's tags: 1.0 s to 1.3 s of CPU per call. Only a tag table or full-text search removes that. Both change results or code, so they are vendor work.
Proof
Same result: 8 of 8 calls identical, 230 rows compared with EXCEPT both ways, row order included. 1 call returns no rows on both sides; it shows cost only, not identity.

Fix 05. Make the top answerers report cheap for every date range

SQL Server compiles a procedure's plan for the parameters of its first call and reuses it. For a one-day range it picks a seek plus one lookup per row. That is right for a day and very wrong for a year. Each test call below first clears the plan, then runs one call to choose the cached plan, then measures the call that has to live with it. Adding OwnerUserId to the index from fix 04 covers the report, so every range is one seek and one range read, whatever ran first. No OPTION (RECOMPILE) was needed.

Result
A year after a day plan: 8,791,501 reads and 24.1 s → 3,384 reads and 588 ms. One day: 12,671 → 82 reads.
Cost
77 s to rebuild the index from fix 04 with one more column.
Proof
Same result: 6 of 6 calls identical, 120 rows compared with EXCEPT both ways, row order included.

Fix 06. Drop the index nobody reads

IX_Posts_LastActivityDate was never read during the workload. None of the plans in Query Store reads it. Three write plans maintain it, because it carries ViewCount and Score, which change on every page view and vote. Writes below run inside a transaction that rolls back, so the data stays the same.

Result
A page view: 7 → 4 reads. A vote: 19 → 16. 94 MB freed.
Proof
Dropping an index cannot change a result. The proof here is that nothing uses it: 0 seeks, scans and lookups in the index counters, and 0 Query Store plans that read it (evidence-before-drop.txt). A rare monthly job could still need it, so the rollback script stays with the change.

Fix 00. Turn AUTO_CLOSE off

The first workload run lost its index counters the moment it ended. The error log showed why: the database started 11 times in 28 minutes with no server restart. Two of those starts were setup steps; the rest were AUTO_CLOSE. With AUTO_CLOSE on, every time the last connection leaves, SQL Server closes the database and throws away its cached pages and plans. Express creates databases this way by default. The baseline in this report was taken after this change.

The workers send the next call as soon as the last one returns. So when calls got faster, they sent more: 184,662 calls instead of 14,846. That is why the summary compares CPU and reads for the same calls: the after-run average per call, times the before-run number of calls, procedure by procedure.

Even with 12 times the calls, the data file served 3.0 GB of reads instead of 967 GB. The disk was never slow: 0.82 ms per read on average. The volume was the problem.

One call got more expensive. A vote reads 18 pages instead of 8, because two of the new indexes carry columns a vote changes. It still takes 3 ms, and votes are a small share of the traffic.

What is left. The tag page is now 94% of the CPU that remains, at 1.2 s per call. Its hash join also spills to tempdb: up to 43 MB per call, and 28 GB over the after run. The next step is the tag table or full-text search in section 5. That needs the vendor.

5. What to clear with the app vendor

A database behind a vendor app is shared ground. These items touch objects the vendor ships, or need their answer:

  • New and changed indexes (fixes 01, 04, 05). Some vendors drop unknown indexes during upgrades, and some refuse support while they exist. Ask whether they accept them, or will ship them in their next release.
  • Dropping their index (fix 06). Ask if any report, job or upgrade script reads it. It was unused for this workload only.
  • Procedure edits (fixes 02 and 03). Their next upgrade will overwrite them. Send them the scripts so the fix lands in their code.
  • The CRM id column type. The cleaner fix for 02 is in the app: send the parameter as varchar, or make the column nvarchar.
  • Search and tags. Full-text search or a tag table would remove the remaining scan. Both change results slightly, so they are a product decision.
  • Read committed snapshot and the compatibility level. Both are database settings the vendor should confirm they support.

6. How this was done

  • Read-only access was enough for the audit: VIEW SERVER STATE and VIEW DATABASE STATE. Ten scripts collect settings, waits, file latency, Query Store top queries with their waits and tempdb use, index usage, missing-index hints, plan warnings and parameter sensitivity.
  • The fixes were tested on a copy, never on the live server. A fix is done when every row matches, not when it "should" match.
  • Fewer reads at a higher elapsed time counts as a regression, not a win.
  • A rewrite that uses existing indexes comes before a new index. Every index here has its build time and write cost next to it.
  • The database is the public StackOverflow2010 copy (Stack Exchange data dump, cc-by-sa 4.0) with a small app built on top of it to play a vendor system. Every number comes from a run in this repository, and the scripts reproduce it.
